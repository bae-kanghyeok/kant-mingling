# KANT Mingling 개선 로드맵

이 문서는 현재 동작하는 버전을 유지하면서 수강생 수와 운영진 구성이 다른 행사에도 재사용하기 위한 계획이다. **아래 확장 제안은 구현 완료를 뜻하지 않는다.** 현재 지원 범위는 소스와 기존 테스트를 기준으로 구분했다. 기준일은 2026-09-22다.

**6인 검증 선행 완료:** develop에서 호스트 1명+참가자 5명의 단일 조를 지원한다. 이동 인원 0명, 3블록·9게임이며 같은 좌석을 유지한다. 개발 DB 통합 테스트에서 9게임, 호스트를 포함한 투표, Noise·Ensemble·Ground Truth, 일시정지·재개, 다음 블록과 종료가 통과했다. 기존 21명 감독 모드를 변경한 것이 아니며 여러 운영진을 가진 단일 조는 별도 과제다. [실참여 안내](six-person-rehearsal.md)를 따른다.

**운영 비용 선행 과제:** 규모 확장 전에 현재 전체 행사 snapshot 조회와 가상 참가자 반복 조회의 DB 전송량부터 줄인다. 상태 버전 확인·조회 범위 축소·로컬 DB 리허설·사용량 측정을 P0으로 다룬다. 원인과 검증 조건은 [문제 해결 안내](troubleshooting.md)에 있다. 이번 UI 개편은 쿼리 최적화를 구현한 것이 아니다.

## 1. 브랜치와 배포 원칙

| 대상 | 역할 | 반영 기준 |
| --- | --- | --- |
| `main` | 현재 검증된 행사 진행 버전과 설치·운영 안내 | 수정 검토 및 필요한 검증을 마친 변경만 병합 |
| `develop` | 회사 디자인 적용, 설치 편의 개선, 인원·역할 확장 | Preview와 개발 DB에서 검증하며 단계별로 진행 |
| 기능 브랜치 | `develop`에서 분리한 하나의 변경 | UI, 역할 모델, 명단 편집 등 검토 가능한 단위로 작업 |

`main`에 있는 기능과 `develop`에서 제안·구현 중인 기능은 릴리스 노트에서 구분한다. 행사에 쓰는 커밋을 태그로 남기고, 운영 배포는 검증된 태그 또는 `main` 커밋을 대상으로 한다. 브랜치를 만들었다고 Vercel의 운영 브랜치나 DB 연결이 자동으로 분리되는 것은 아니다. Vercel Production은 운영 DB, Preview·로컬은 개발 DB를 사용하도록 별도로 확인한다.

UI 개편도 먼저 `develop`에서 참가 등록, 프로필, 게임, 관제까지 확인한다. 게임 규칙·API의 정보 공개 범위·세션 복구를 유지한 상태로 검증한 뒤 `main`에 반영한다. 운영 중인 행사의 화면과 데이터 구조를 동시에 바꾸는 배포는 피한다.

## 2. 현재 이미 구현된 범위

| 항목 | 현재 구현 | 근거 |
| --- | --- | --- |
| 수강생 수 | 18명 고정이 아니다. 활성 학생 수와 설정값이 일치해야 하며, 학생 수는 조 수 이상이어야 한다 | `src/server/game/settings.ts` |
| 조 수 | 설정과 명단에서 1~26개 조를 허용한다. A부터 이어지는 조 이름을 사용하며 단일 조는 이동 인원 0명만 허용한다 | `settings.ts`, `scripts/helpers/event-admin.mjs`, DB `teams.team_key` |
| 불균등 인원 | 학생 수가 조 수로 나누어떨어지지 않아도 인원 차이 1명 이내로 처음 배정한다 | `getStudentCapacities`, `src/server/game/teams.ts` |
| 운영진 수 | 활성 운영진 수가 조 수와 같아야 한다. 각 조에 정확히 1명을 배정한다 | `validateRosterConfig`, `createInitialAssignments` |
| 전체 호스트 | 운영진 중 1명이다. 전체 조 편성·시작·다음 블록·종료·설정·명단을 제어하고 모든 조를 관리할 수 있다 | `admin-service.ts`, `services/shared.ts` |
| 조 운영진 | 자신의 조 진행을 관리한다. 전체 호스트와 권한이 구분되어 있다 | `controlledTeam`, `requireHost` |
| 호스트 교체 | 관제의 호스트 이전과 관리 스크립트를 제공한다. 활성 운영진에게 이전한다 | `transfer-host`, `scripts/set-host.mjs` |
| 명단 변경 | 참가자 추가·수정·비활성화가 있다. 준비 중 변경은 편성안을 다시 만들고, 진행 중 변경은 다음 블록에 반영한다. 마지막 블록에서는 명단 변경을 막는다 | `rosterChange`, `src/server/services/block-service.ts` |
| 조 변경 | 다음 블록의 조 증가·감소, 학생 추가·제외, 운영진 교체에 맞춰 재편성하는 계산이 있다 | `src/server/game/rotation.ts` |
| 게임 참가 조건 | 현재 조의 활성·비결석·프로필 완료자 중 최소 2명이 필요하다. 운영진도 조건을 충족하면 게임 참가자에 포함된다 | `src/server/services/game-service.ts` |
| 설정 적용 시점 | 조별 규칙 변경은 다음 Game, 전체 설정은 다음 블록에 적용한다. 이미 생성된 게임은 설정과 참가자 스냅샷을 유지한다 | `game-service.ts`, `block-service.ts` |
| 재접속 | 같은 유효 세션이면 상태를 복원한다. 학생의 다른 기기 재접속은 운영진 잠금 해제 후 같은 이름으로 재등록하는 경로가 있고, 운영진은 코드로 재인증할 수 있다 | `registration.ts`, 세션 복구 테스트 |
| 연결 장애 대응 | 연결 상태 표시, 폴링 재시도, 조 일시정지·재개, Turn Lead 이전, Data 재전송, 강제 공개가 있다 | `useMingleState.ts`, `admin-service.ts` |

따라서 다음 개선은 “인원 가변 기능을 처음 만드는 작업”이 아니다. **이미 있는 편성 기능을 설치·설정 화면과 운영 절차로 연결하고, 운영진과 조 수의 결합을 풀어주는 작업**이 중심이다.

현재 단위 테스트에는 학생/조/이동 인원 조합 `18/3/3`, `11/4/2`, `7/2/1`, `12/3/0`, 조 추가·제거 및 운영진 교체 사례가 있다. 이 결과는 편성 계산의 검증이며, 모든 조합을 실제 기기로 전체 행사 진행한 결과는 아니다. DB 통합 테스트는 설정 적용 시점, 권한, 중복 요청, 세션 복구와 기본 행사 흐름을 검증한다.

## 3. 현재 지원으로 오해하면 안 되는 제한

- **운영진과 조 수는 독립적이지 않다.** 조마다 운영진 2명을 두거나, 한 운영진이 여러 조를 맡거나, 게임에 참여하지 않는 전담 호스트를 두는 역할 모델은 아직 없다. 전체 호스트를 동시에 여러 명 두는 기능도 없다.
- **호스트는 별도 참가자가 아니라 운영진의 추가 권한이다.** 프로필 작성·좌석 배정·정답 후보 여부가 운영 권한과 아직 분리되지 않았다.
- **조 수 26은 입력 제한이다.** 최대 동시 접속 규모나 성능 보장이 아니다. `studentCount`에 상한이 없더라도 임의 규모의 행사를 지원한다고 표현하지 않는다.
- **기본 Ensemble은 조 인원에 영향을 받는다.** 현재 게임 참가자 수의 절반을 올림한 Data 번호에서 시작한다. Data가 최대 20개이므로 41명 이상의 게임 참가자는 기본 설정으로 유효한 시점을 만들지 못한다. 전체 행사 규모와 조별 인원을 따로 검증해야 한다.
- **3블록·블록당 3Game·최대 9Game·프로필 20문항은 고정되어 있다.** DB 제약, 화면, 게임 전환, 테스트에 걸쳐 있으므로 인원 변경과 별도 단계로 다룬다.
- **명단과 설정은 한 번에 저장되지 않는다.** 현재는 명단 수정 후 조 수·배정 등을 맞추는 중간 상태가 생길 수 있다. 불완전한 다음 편성안은 게시되지 않지만 운영자가 원인을 파악하고 고쳐야 한다. 새 운영진 코드도 별도로 발급한다.
- **동명이인은 지원하지 않는다.** 행사 내 표시 이름이 고유해야 하며 일부 운영진 배치는 이름으로 연결된다.
- **회복 기능은 DB 초기화가 아니다.** 쿠키·세션·관제 상태를 복구하는 기능과 DB 장애·잘못된 배포에서 회복하는 운영 절차를 구분한다.
- **리허설과 부하 도구는 기본 21명에 맞춰져 있다.** `scripts/rehearsal.mjs`, `scripts/load-test.mjs`, 개발 seed와 주요 통합 fixture의 인원도 확장 시 함께 바꿔야 한다.
- **입장 제한과 동시성에 규모 가정이 있다.** 새 세션 생성은 행사·IP별 60초에 30회 제한이 있다. 동일 Wi-Fi에서 많은 참가자가 입장하거나 재시도할 때의 동작을 검증해야 한다. 게임·관제의 일부 명령은 행사 행 잠금으로 직렬화된다.
- **자리 교체는 표본 탐색이다.** 기본 30,000회 후보 탐색으로 반복 만남을 줄이며 최적 배치를 보장하지 않는다. 인원 증가 시 계산 시간과 잠금 유지 시간을 측정해야 한다.

## 4. 단계별 개선 순서

### P0. 안정본 보존과 공개 설치 기준 정리

현재 게임을 `main` 기준으로 보존하고, 합성 명단만 포함한 재현 가능한 설치·리허설 경로를 제공한다. 사람용 안내와 AI 에이전트용 안내는 같은 명령·환경변수·완료 조건을 가리키도록 맞춘다. 회사 디자인 파일·자산은 출처와 사용 범위를 기록하고, 소스 공개 범위와 로컬 보관 범위를 구분한다.

완료 조건: 새 작업 폴더와 별도 개발 DB에서 문서만 따라 설치·마이그레이션·합성 행사 생성·호스트 입장·첫 Game 시작이 가능하다. 특정 작성자의 PC 경로, Neon endpoint, Vercel 계정에 의존하지 않는다. 명단·운영진 코드·환경변수 값이 공개 저장소나 배포 산출물에 들어가지 않는다.

### P1. 기존 인원 가변 기능을 쓰기 쉽게 만들기

행사 설정에서 학생 명단, 운영진 명단, 조 수, 조별 정원, 이동 인원을 한 초안으로 편집하고 한 번에 검증·저장한다. 현재/다음 블록에 적용될 내용을 나란히 보여주고, 편성안을 공개하기 전에 인원 불일치·프로필 부족·이동 불가 사유를 표시한다. 진행 중인 게임의 구성은 그대로 두고 다음 블록 공개 시에만 새 구성을 적용한다.

운영진 배치는 표시 이름 대신 참가자 ID로 연결하도록 전환한다. 중복 이름을 허용하려면 등록 화면에서 구분 이름이나 짧은 식별번호를 제공하고 기존 고유 제약·명단 검증을 함께 변경한다. 기존 행사 데이터에서 이름 변경이나 비활성화가 과거 게임의 정답 공개 기록을 훼손하지 않는지도 확인한다.

리허설과 fixture에 인원·조 수 옵션을 추가하여 실제 행사와 같은 구성을 생성한다. 불가능한 조합은 생성 전에 설명하고, 단순히 입력 필드의 최대 숫자만 늘리지 않는다.

완료 조건: 아래 수용 테스트의 기본 가변 인원·명단 변경 사례가 UI부터 DB까지 통과한다. 기존 18명+운영진 3명 행사도 같은 결과로 진행된다.

### P2. 운영 권한과 게임 참여를 분리하기

다음은 구현 전 확정할 제안 모델이다.

| 개념 | 제안 |
| --- | --- |
| 전체 책임 호스트 | 행사당 기본 1명. 설정·명단·전체 시작·종료·호스트 이전 책임을 가진다 |
| 공동 관리자 | 필요 시 여러 명에게 전체 관리 권한을 부여한다. 역할 부여와 최종 책임 호스트 변경은 별도 권한으로 둔다 |
| 조 운영진 | 사람과 조를 다대다로 연결해 조당 여러 운영진 또는 운영진 1명의 여러 조 관리를 허용한다 |
| 게임 참여 여부 | 운영 권한과 별도 속성으로 둔다. 전담 호스트는 프로필·좌석·정답 후보·단서 수신 대상에서 제외할 수 있다 |
| 학생 | 게임 참가 권한만 가진다. 클라이언트에서 역할·조 정보를 보내도 서버에서 실제 권한을 다시 검증한다 |

핵심은 “호스트 수”를 숫자 하나로 늘리는 대신 **전체 행사 제어 권한, 조 제어 권한, 게임 참여 여부를 나누는 것**이다. 한 명의 전체 책임 호스트를 기본으로 유지하되 보조 관리자 수는 조 수와 독립적으로 정한다. 운영진이 없는 조를 허용할지, 전담 호스트 한 명이 모든 조를 관리할지, 보조 관리자의 종료 권한을 어디까지 줄지는 이 단계 시작 시 제품 규칙으로 확정한다.

DB는 기존 단일 호스트와 조별 운영진 필드에서 역할·조 연결 구조로 옮기되, 먼저 기존 데이터를 읽을 수 있는 추가 구조를 만들고 검증 후 전환한다. 단일 필드를 바로 제거하는 마이그레이션은 하지 않는다. 과거 게임의 참가자·정답·투표 스냅샷은 변경하지 않는다.

여러 관리자의 동시 조작은 기존 `requestId` 영수증, 버전 검사, 트랜잭션 원칙을 확장한다. 서로 다른 관리자가 다음 Game을 동시에 누르면 한 번만 생성되어야 한다. 권한이 바뀐 사람의 다음 요청에는 즉시 새 권한이 적용되어야 한다. 어떤 관리자에게도 공개 전 정답이나 다른 사람의 비공개 Data를 추가로 보내지 않는다.

완료 조건: 전담 호스트 1명+여러 조, 한 조의 운영진 2명, 공동 관리자와 조 운영진의 동시 조작이 역할별 수용 테스트를 통과한다. 기존 데이터의 마이그레이션·되돌림 절차를 실제 개발 DB에서 검증한다.

### P3. 규모·장애 대응 범위 넓히기

먼저 지원할 참가자 수와 조별 권장 인원을 정하고 그 규모에서 측정한다. 폴링 간격, 연결 수, 응답 지연, DB 오류, 행사 잠금 대기, 자리 교체 시간, 동일 IP 입장을 함께 측정한다. 정상 참석자 입장을 보장하면서 남용 방지도 유지할 수 있도록 입장 제한을 조정한다. 측정 없이 WebSocket이나 새 인프라를 추가하지 않는다.

응답을 잃은 명령은 같은 `requestId`로 결과를 확인·재시도할 수 있도록 클라이언트 흐름을 보강한다. 현재 서버의 중복 처리 방지와 “연결을 잃었으니 새 명령을 한 번 더 실행”하는 UI 동작을 혼동하지 않게 한다. 호스트 기기 분실, 전체 브라우저 새로고침, 일시적 DB 불가, 배포 되돌림을 각각 리허설한다.

행사별 DB 백업·복원·데이터 보관 기간, 검증된 배포로 되돌리는 순서, 호스트 코드 재발급·이전 경로를 운영 안내에 정리한다. 게임 복구를 위해 행사 데이터를 삭제하는 절차를 기본 대응으로 두지 않는다.

완료 조건: 합의한 규모에서 입장부터 종료까지 진행하고, 실패 주입 후 참가자 식별·답변·현재 좌석·게임 단계·투표 마감이 보존된다. 지원 규모와 측정 환경을 릴리스에 명시한다.

### P4. 행사 형식의 범용화

인원·역할 확장이 안정화된 뒤 블록 수, 블록별 Game 수, 프로필 문항 수, 행사명·일정·문구를 설정으로 옮길지 검토한다. 문항별 원문과 콘텐츠 버전을 게임 스냅샷에 연결하여 새 질문을 배포해도 진행 중인 행사의 의미가 바뀌지 않게 한다. 현재 20문항과 Noise·Ground Truth·Ensemble 규칙은 별도 승인을 받은 변경 단위로 다룬다.

## 6. 다음 개발 착수 전에 정할 것

1. 첫 확장 릴리스의 실제 목표 참가자 수와 조별 권장 인원.
2. 게임에 참여하지 않는 전담 호스트가 필요한지, 공동 관리자가 전체 종료까지 할 수 있는지.
3. 운영진 없는 조와 운영진 1명의 여러 조 관리를 허용할지.
4. 인원·명단 변경을 다음 블록에 적용하는 현재 정책을 유지할지.
5. 3블록·9Game·20문항의 형식은 이번 확장에서 유지할지.

이 결정 전에도 P0의 설치 재현성과 P1의 현재 기능 안내·초안 검증은 진행할 수 있다. 역할·규칙 변경은 문서의 제안을 그대로 현재 기능으로 간주해 적용하지 않는다.
