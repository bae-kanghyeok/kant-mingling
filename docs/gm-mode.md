# GM과 함께 진행하는 KANT Mingling

이 문서는 조 운영진이 대화의 흐름을 조절하는 GM 모드의 운영 기준이다. 참가자는 취향을 나누고 추리하며, GM은 다음 단서·추리·투표·다음 판을 진행한다. 판을 빨리 끝내거나 많이 끝내는 것은 목표가 아니다.

> 상태: 제품 소스 `7acb834`의 GM 기능을 `develop`에 구현하고 Preview의 4인 HTTP 진행과 모바일 크기 브라우저 화면을 확인했다. 새 행사에 `gameplayMode: "gm"`을 지정해야 적용되며 기존 행사는 classic 방식으로 유지된다. 실제 사람의 대화 효과·실물 기기·GM 21인 운영은 별도 확인이 필요하다. 상세 범위는 아래 검증 기록을 참고한다.

## 1. 역할

| 역할 | 하는 일 | 공개 전 볼 수 없는 정보 |
| --- | --- | --- |
| 플레이어 | 프로필 작성, 받은 단서 공유, 자신의 선택·경험 이야기, 투표, 허용된 차례에 추리 제출 | 다른 사람의 전체 프로필, Owner 정답, 실제/Noise 구분, Noise의 원래 답 |
| 조 GM | 플레이어 역할을 함께 수행하면서 자기 조의 다음 단서·추리 열기·투표·토론 마침·다음 판 시작을 제어 | 플레이어와 동일. 진행 권한은 정답 열람 권한이 아님 |
| 총괄 GM | 자기 조 GM을 겸하며 전체 조의 상태 확인, 자리 이동 요청·확정, 행사 종료 | 다른 GM과 동일 |

조마다 GM 1명이 배치된다. GM도 같은 20문항에 답하고 Owner 후보가 된다. GM이 자기 조의 진행을 조절하는 동안 다른 조의 진행 속도는 영향을 받지 않는다. 총괄 GM은 필요하면 관제에서 다른 조의 일시정지·재개·강제 공개를 돕는다. 일반 단서·추리 진행은 각 조 GM이 자기 리모컨으로 조절한다.

각 판은 담당 GM이 프로필을 제출하고 출석해 함께 참여할 수 있어야 시작된다. ‘조 GM의 프로필과 출석을 확인해주세요’가 보이면 담당 GM의 제출·출석 상태를 확인한다.

## 2. 참가자에게 처음 설명하기

> 우리 조 안에 숨어 있는 ‘취향의 주인공’을 찾아볼 거예요. 한 분이 미리 고른 답이 단서로 하나씩 나옵니다. 질문이 나오면 여러분도 어느 쪽인지 골라보고, 이유를 함께 이야기해주세요. 그러다 “이 사람 같은데?” 싶으면 추리에 도전할 수 있어요. 뒤에는 진짜 답과 다르게 바뀐 단서도 등장하니 서로 이야기하며 찾아보겠습니다. 혹시 내 답인 것 같아도 정체는 공개할 때까지 잠깐 참아주세요!

추리 후보가 아닌 것 같아도 계속 대화에 참여한다. 자기 선택이 단서와 다르다는 것은 그 질문에 대해 이야기할 수 없다는 뜻이 아니다. 정답을 알 것 같다는 이유로 다른 사람의 이야기를 끊지 않는다.

## 3. 한 판의 진행

등록·프로필 작성·조 배정은 기존과 같다. 차이는 게임 중 다음 단계로 넘어가는 시점을 조 GM이 결정한다는 점이다.

1. **GM이 판을 시작한다.** 행사 첫 시작은 총괄 GM이 모든 조를 함께 시작한다. 이후 같은 조의 다음 판과 이동 뒤 착석 완료 시작은 조 GM이 제어한다. 다음 판의 Noise 최대 개수와 Ground Truth 사용 여부를 확인하며, 시작한 판의 설정은 중간에 바뀌지 않는다.
2. **단서를 받은 사람이 읽는다.** 질문의 두 선택지와 표시된 답을 함께 읽는다. 일반 단서 본문은 기존처럼 해당 수신자의 화면에 보인다.
3. **모두 선택과 경험을 나눈다.** GM은 “여러분은 어느 쪽이에요?”, “같은 선택인데 이유가 다르네요”처럼 대화를 연다. 매번 모든 사람이 긴 답을 해야 하는 절차로 만들 필요는 없다.
4. **GM이 참가자 의견을 듣고 진행한다.** “지금 추리해볼까요, 단서를 하나 더 볼까요?”라고 묻는다. 다음 단서를 고르면 GM이 바로 전달하고, 추리를 고르면 현재 진행권자의 추리 입력을 연다.
5. **진행권자가 추리를 제출한다.** GM이 추리 입력을 열어도 실제 답은 해당 진행권자가 제출한다. 첫 판은 단서 1개부터, 이후 판은 단서 3개부터 추리할 수 있다. 오답 뒤에는 허가가 닫히고 새 단서가 필요하다. GM이 대화를 이어간 뒤 다음 단서를 보내고 다시 추리를 열어준다. 20개 단서를 다 본 경우에는 새 단서를 요구하지 않고 GM이 재추리를 열 수 있다.
6. **정답 공개 뒤에도 이야기한다.** “어떤 단서에서 눈치채셨어요?”, “그 선택에는 특별한 이유가 있었나요?”로 마무리한다. 공개만으로 다음 판이나 자리 이동이 자동 실행되지는 않는다.
7. **GM이 다음 판 또는 이동 준비를 선택한다.** 이동 요청이 없다면 다음 판 설정을 확인하고 시작한다. 이동 요청이 왔다면 현재 판과 후속 대화를 마친 뒤 준비 완료를 표시한다.

추리 버튼이 열렸다는 사실은 정답 여부에 관한 힌트가 아니다. GM은 공개 전 정답을 모른다. 참가자에게 기다리는 이유와 다음 동작을 알려줘야 한다. 예: “지금은 이야기 나누는 시간이에요. GM이 추리를 열면 답을 제출할 수 있어요.”

## 4. GM 리모컨

| 조작 | 언제 사용하는가 | 기대 결과 |
| --- | --- | --- |
| 다음 단서 | 대화 중인 TURN 단계에서 단서를 더 보기로 했을 때 | 새 단서가 기존 전달 규칙에 따라 전달된다. 참가자의 추가 클릭은 필요 없다 |
| 추리 열기 | 대화 뒤 팀이 지금 추리하기로 했을 때 | 현재 진행권자의 추리 입력이 열린다. 다른 참가자는 대신 제출할 수 없다 |
| 추리 닫기 | 입력을 열었지만 대화를 더 하기로 했을 때 | 제출 허가를 닫는다. 새 단서·진행권 변경 등으로도 기존 허가가 닫힌다 |
| Ensemble 투표 시작 | 단서 공유와 대화가 끝났을 때 | 투표 시간이 시작된다. 단서 수신자가 잘못 눌러 대화를 조기에 끝내지 않는다 |
| Ensemble 토론 마침 | 집계 후 필요한 이야기를 나눴을 때 | 다음 진행 단계로 돌아간다 |
| 다음 판 시작 | 정답 공개 뒤 대화를 마쳤고 이동 요청이 없을 때 | 확인한 설정으로 새 판이 시작된다 |
| 이동 준비 완료 | 총괄의 이동 요청 후 현재 판과 대화를 마쳤을 때 | 자기 조가 기다림 상태로 바뀐다 |

리모컨의 화면 이름은 구현에 따라 약간 달라질 수 있다. 새로고침이나 다른 창에서의 조작 이후에는 서버가 반환한 최신 상태를 기준으로 허용 버튼이 바뀐다. 화면에 버튼이 없더라도 서버가 같은 권한·상태 조건을 검사한다.

GM도 Ensemble 투표에 참여한다. 관제 리모컨을 열어둔 채 투표를 시작했다면 **내 투표 화면으로**를 눌러 리모컨을 닫고 자기 표를 제출한다. 투표는 모든 참가자의 개인 화면에서 진행된다.

진행권자에게 단서가 전달되지 않았거나 연결이 끊긴 경우에는 관제의 복구 기능을 사용한다. 특정 GM이 받은 적 없는 단서를 관제 권한만으로 열어볼 수 있게 하지는 않는다.

## 5. Noise 설정

- GM은 **다음 판의 Noise 최대 개수**를 0~5에서 고른다.
- ‘2개’는 그 판에서 최대 2개까지 등장할 수 있다는 뜻이다. 2개가 모두 나올 때까지 정답을 막거나 강제로 단서를 더 보지 않는다.
- 설정값보다 적은 Noise만 나온 상태에서도 맞히면 그 판을 끝낼 수 있다.
- 각 조가 행사에서 진행하는 **전체 첫 판만** Noise 없이 시작한다. 자리를 이동했다고 다시 첫 판으로 취급하지 않는다.
- 설정을 바꿔도 이미 시작한 판에는 영향을 주지 않는다.
- 첫 판 이후 기본 설정은 Noise 최대 1개·Ground Truth 끔이다. GM이 필요에 맞춰 바꾼다.
- Noise 최대 개수는 난도 조절 수단이다. 대화가 짧다는 이유만으로 개수를 높이는 것은 대화 운영을 대신하지 못한다.

화면의 ‘다음 판 최대 개수’와 실제로 지금까지 전달된 Noise 개수는 서로 다른 정보다. 최대 개수 설정이 공개 전 Noise 카드의 위치나 실제 개수를 드러내서는 안 된다.

Ground Truth는 실제 단서를 하나 확인해주는 기능이다. 전체 첫 판에서는 사용하지 않고, 이후에는 GM이 다음 판 설정에서 사용 여부를 고른다. Noise와 마찬가지로 시작한 판의 설정은 고정된다. 예전처럼 특정 고정 판 번호에 도달해야 사용할 수 있는 방식이 아니다.

## 6. 조별 진행과 자리 이동

같은 시간에 A조는 첫 판의 대화를 계속하고 B조는 다음 판을 진행할 수 있다. 한 구간에서 정확히 세 판을 끝낼 필요는 없고 구간도 세 번으로 제한하지 않는다. 총괄 GM이 행사 종료를 결정한다. 전체를 ‘9판 완주’로 안내하지 않는다.

1. 총괄 GM이 **자리 이동 준비를 요청**한다.
2. 각 조 GM은 현재 판과 공개 후 대화를 마무리한다. 이동 요청이 오면 모든 조가 새 판을 시작할 수 없고, 현재 판은 계속 진행할 수 있다.
3. 각 조 GM이 **이동 준비 완료**를 표시한다.
4. 모든 조가 준비되면 총괄 GM이 **자리 이동을 확정**한다.
5. 새 배정과 착석 안내에 따라 이동한 후 각 조 GM이 ‘착석 완료 · Game 시작’을 누른다. 한 조 리허설은 같은 자리에 머물며 준비 완료 후 시작한다.

3조 운영에서는 조별 학생 3명이 이동하고 운영진은 담당 조에 남는다. 실제 이동은 설정과 배정 검증을 따른다. 한 조만 있는 4~6인 리허설에서는 이동 인원이 0명이다. 조별 진행 검증과 다조 이동 검증은 별개다.

모든 조가 준비되기 전에는 총괄 GM이 이동 요청을 취소할 수 있다. 그러면 각 조의 준비 완료 표시도 해제된다. 전 조 준비 완료 뒤에는 배정안을 확인하고 이동을 확정한다.

행사 종료는 총괄 GM이 실행한다. 진행 중인 판을 어떻게 마무리할지 확인한 뒤 종료하고, 자동 타이머만으로 행사를 끝내지 않는다.

## 7. 4명·6명으로 리허설하기

두 경우 모두 **GM 1명을 포함한 한 조**로 시험할 수 있다. 인원이 적어도 GM은 프로필을 작성하고 게임에 참여한다.

새 개발 리허설은 `templates/roster-gm.example.json`을 Git에서 제외되는 `.local.json` 명단으로 복사해 만든다. 이 템플릿에는 `"gameplayMode": "gm"`이 포함돼 있다. 기존 리허설의 모드를 자동 변경하거나 기존 행사 데이터를 초기화하지 않는다.

- 4명: GM 1명 + 플레이어 3명. 6자리 합성 명단을 사용하는 경우 미참여 2명을 결석 처리한 뒤 편성한다.
- 6명: GM 1명 + 플레이어 5명.
- 각자 별도 기기 또는 독립 브라우저 세션으로 접속한다. 한 브라우저의 일반 탭 여러 개는 서로 다른 참가자 검증을 대신하지 않는다.
- 프로필 제출 → 조 편성 → 배정 공개 → 첫 판 시작을 확인한다.
- 최소 한 번은 ‘대화 → 다음 단서’, 한 번은 ‘대화 → 추리 열기 → 참가자 제출’을 진행한다.
- Noise가 있는 판, Ensemble, 새로고침 복구, 공개 후 대화, 이동 준비와 종료를 각각 확인한다.

21명·3조 합성 행사는 학생 18명과 GM 3명, 호스트 1명 겸임, 이동 인원 3명으로 새 명단을 만든다. 각 학생은 `학생01` 같은 합성 이름, GM은 `운영진A`·`운영진B`·`운영진C`, 조 키는 A·B·C를 사용한다. 기본 6명 템플릿에서 참가자 수만 생각 없이 늘리지 말고 운영진·조 배정·이동 수를 함께 맞춘다. 생성 명령은 [README](../README.md#설치와-배포)를 참고한다.

구체적인 접속 주소와 인증 코드 수령 방법은 해당 리허설의 별도 안내를 사용한다. 이 공개 문서에 운영진 코드나 실제 명단을 기록하지 않는다. 이전 배포용 안내의 주소에 최신 코드가 자동 반영됐다고 가정하지 않는다.

사람이 바로 진행할 순서와 4명 출석 처리는 [GM 리허설 시작 안내](gm-human-rehearsal.md)에 있다. 이전 [4~6인 안내](human-rehearsal-4-to-6.md)는 classic 검증 당시의 기록이다.

## 8. 리허설에서 평가할 것

**기능 확인**은 버튼·권한·투표·상태 복구·자리 이동이 올바르게 동작하는지 보는 것이다. **사람 대상 평가는** 서로 대화하기 쉬워졌는지 보는 것이다. 하나의 통과가 다른 하나의 성공을 뜻하지 않는다.

- 조용한 사람도 자신의 선택 이유를 말할 기회가 있었는가?
- 추리 후보에서 제외된 뒤에도 대화에 참여했는가?
- 참가자가 다른 참가자에게 후속 질문을 했는가?
- 참가자들이 스스로 “한 장 더 보자”, “지금 맞혀보자”라고 제안했는가?
- GM의 버튼 조작 때문에 대화가 끊기거나 참가자가 이유 없이 기다리지 않았는가?

정답률·완주 판 수·빠른 클리어만으로 밍글링 효과를 평가하지 않는다. AI 참가자 모사는 기능 감사에 도움이 되지만 사람들의 재미·친밀감·현장 대화량을 검증하지 못한다.
