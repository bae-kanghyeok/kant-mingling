# 게임과 기술 개요

## 참가 흐름

`/e/<slug>` 접속 → 명단에서 본인 이름 선택 → 운영진만 코드 인증 → A/B 20문항 작성 → 조 배정 → 조별 게임 → 정답 공개 후 대화 → 자리 이동 → 마지막 대화와 호스트 전체 종료.

행사 설정의 `gameplayMode`가 `"gm"`이면 GM 모드, 미지정 또는 `"classic"`이면 기존 모드다. 새 migration을 적용해도 기존 행사가 GM 모드로 바뀌지 않는다. 시작한 행사의 모드 변경은 서버가 거절한다. 조별 진행은 독립적이고 참고 타이머는 게임을 자동 종료하지 않는다. 각 조 운영진은 플레이어와 GM을 겸한다. 일반 GM 리모컨 UI는 자기 조 중심이며, 총괄의 타조 관제 UI는 일시정지·재개·강제 공개 같은 복구 조작을 제공한다. 서버의 총괄 대리 권한이 모든 타조 리모컨 버튼의 UI 제공을 뜻하지 않는다.

Data Owner는 서버가 고른다. 단서 수신자가 팀원에게 질문과 표시 답을 공유하고 함께 대화한다. Noise는 실제 선택의 반대 답이다. Ensemble에서는 공유·개별 투표·토론이 진행되고 Ground Truth는 실제 단서 하나를 확인한다. 정답 뒤에는 Behind the Data 질문으로 대화를 이어간다.

## 모드별 진행

| 구분 | classic | GM |
| --- | --- | --- |
| 다음 단서 | 현재 Turn Lead의 `more-data` | 조 GM/총괄의 `next-card`. 학생의 `more-data`는 거절 |
| 추리 | 최소 단서 등 기존 조건 충족 시 Turn Lead가 제출 | GM의 `open-guess` 이후 현재 Turn Lead가 제출. `close-guess`로 닫기 가능 |
| 추리 허가 소진 | 별도 허가 없음 | 새 단서·오답·공개·진행권 변경·Ensemble 토론 종료 때 닫힘 |
| Ensemble | 공유자 및 운영진이 공유 확인·토론 종료 가능 | GM/총괄이 공유 확인 후 30초 투표를 시작하고 토론 종료 |
| 다음 판 | 블록당 3판, 전체 9판 | 조별 연속 번호. 고정 3판/9판 완료 조건 없음 |
| Noise/GT | 판 번호별 기존 설정 | 다음 판 최대 Noise 0~5·GT 사용 여부. 첫 판은 Noise 0/GT 끔 |
| 자리 이동 | 3판 후 모든 조 완료를 기다려 다음 블록 | 총괄 요청 → 조별 준비 완료 → 모든 조 준비 후 총괄 공개 |

GM 모드의 첫 판은 각 조의 행사 전체 첫 판이며, 자리 이동 뒤 초기화하지 않는다. 이후 기본값은 Noise 최대 1개·GT 끔이다. 설정한 Noise 개수를 다 보지 않아도 정답을 맞히면 종료된다. 최소 추리 단서는 첫 판 1개·이후 판 3개다. 각 판의 설정은 `config_snapshot`에 고정되어 다음 판 설정 변경에 영향받지 않는다. 구간도 세 번으로 제한하지 않으며, 판 번호와 구간 번호의 저장 안전 상한은 32,767이다. 4번째 이후 구간의 참고 시간은 세 번째 시간 설정을 사용한다.

## GM 명령과 이동 상태

`start-game1`은 총괄이 전 조 첫 판을 함께 시작한다. 정답 공개 뒤에는 각 조 GM이 `gm-next-game`을 실행하며 `noiseCap`·`groundTruth`를 함께 전달할 수 있다. 새 자리의 `SEATING` 상태에서는 `start-block-game`으로 해당 조를 시작한다. 두 시작 명령 모두 서버에서 새 판 설정을 고정한다.

게임 명령 `next-card`, `ensemble-shared`, `ensemble-end-discussion`은 현재 게임 버전을 확인한다. 추리 허가는 관리자 명령 `open-guess`/`close-guess`로 제어하며 실제 `guess`는 현재 Turn Lead의 참가자 명령이다. `allowedActions`는 UI용 허용 목록이며 서버의 역할·상태 검증을 대신하지 않는다. 해당 조 운영진 또는 총괄만 조를 제어할 수 있다.

이동은 다음 상태 흐름을 따른다.

1. `request-rotation`: 총괄이 현재 `BLOCK`에서 요청. 이때부터 모든 조의 새 판 시작을 막지만 현재 판의 단서·추리·대화는 계속할 수 있다.
2. `rotation-ready`: 현재 판이 공개되고 대화까지 마쳤거나 아직 판을 시작하지 않은 `SEATING` 조가 준비 완료. `rotation_ready=true`, 조 상태는 `BLOCK_DONE`.
3. 모든 조의 준비 완료를 확인하면 서버가 `BREAK`로 옮기고 다음 배정안을 만든다.
4. `publish-next-block`: 총괄이 배정을 공개. 다음 구간 `SEATING`을 만들고 이동 요청을 해제한다. 착석 뒤 각 조가 `start-block-game`을 실행한다.

모든 조가 준비되기 전 `BLOCK` 상태에서는 총괄의 `cancel-rotation`으로 요청과 각 조의 준비 표시를 해제할 수 있다. 총괄 `end-session`은 확인을 요구하며, 진행 중인 판이 있으면 `session_end` 사유로 공개한 뒤 전체를 종료한다. 특정 판 수 달성이나 자동 타이머는 종료 조건이 아니다. 3조 기본 이동은 학생 3명/조, 한 조는 0명이다.

## 구조

| 경로 | 책임 |
| --- | --- |
| src/components | 입장·프로필·게임·관리자 화면과 상태 조회 |
| src/app/api | 인증된 API 진입점과 입력 검증 |
| src/server/game | DB와 분리된 규칙·배정·이동 계산 |
| src/server/services | 트랜잭션 안에서 게임·관리 명령 수행 |
| src/server/dto | 역할·수신 여부에 따른 응답 허용 목록 |
| src/server/auth | 쿠키 세션, 운영진 코드, 호출 제한 |
| db/migrations | 스키마와 체크섬 기반 migration |
| scripts | 설치·명단·개발 DB 테스트·로컬 리허설 |
| tests | 게임 단위 검증과 실제 개발 DB 통합 검증 |

Next App Router와 짧은 폴링을 사용한다. API 명령 뒤에 상태를 다시 조회한다. 세션은 DB에서 복구하고 행사 slug에서 파생한 별도 쿠키 이름으로 다른 행사 방문과 분리한다. 기존 공통 쿠키는 해당 행사 검증을 거쳐 호환한다. 버전·requestId로 충돌과 중복 명령을 처리하며 DB 잠금을 잡은 상태에서 외부 API를 호출하지 않는다.

## 공개 전 데이터 경계

정답 ID, 실제/Noise 구분, 원래 답, Noise 배치, 난수 seed와 추리 내부 지표는 서버 전용이다. 운영진·호스트 응답도 이 경계를 따른다. 일반 카드의 질문 원문과 표시 답은 수신자에게만 보낸다. 2026-09-22 사용자 승인으로 Noise 선택창에는 지금까지 팀에 전달된 모든 단서의 질문·표시 답변을 제공한다. 별도 `game.guess.cards`는 현재 Turn Lead가 실제로 Noise 추리 가능한 때에만 포함하며, GM 모드에서는 추리 열기 여부도 조건에 포함한다. 일반 `cards`·개인 단서 목록과 분리하며 정답·실제 Noise 구분·원래 답은 포함하지 않는다. 정답 공개 후에는 해당 게임 참가자에게 전체 결과를 공개한다.

`COMMON_CARD_FALLBACK`·`RARE_CARD_FALLBACK`·`owner_fallback` 같은 내부 진단은 운영진 화면의 `recentLogs`에서 제외한다. 필드 이름뿐 아니라 카드 수·시점·운영 이력으로 숨겨진 정보를 추론할 수 있는지도 회귀 검사한다. 조 GM에게 리모컨이 있다는 이유로 다른 수신자의 본문이나 정답을 추가 반환하지 않는다.

프로필은 취향과 대화를 위한 정보다. 심리 진단·성격 유형·점수·순위 기능은 없다. 실제 참가자의 이름·답변·운영진 코드는 공개 저장소에 포함하지 않는다.

## 환경과 검증

앱은 pooled DATABASE_URL을 사용한다. migration은 직접 연결 DATABASE_URL_UNPOOLED을 사용한다. 운영 스크립트는 연결 endpoint, DB 환경 표지, 명시적인 운영 인자를 함께 검사한다. 환경 표지를 바꿔 검사를 우회하면 안 된다.

`003_gm_progression.sql`은 이동 요청·조별 준비·추리 허가 상태를 추가하고 판/구간 제약을 확장한다. 기존 migration을 수정하지 않는다. GM 개발 행사는 `templates/roster-gm.example.json`의 합성 명단을 `.local.json`으로 복사하고 `scripts/seed-event.mjs --roster <파일> --slug <새-dev-slug> --synthetic`으로 만든다. 템플릿은 GM 포함 6명 한 조이며 4명은 학생 3명으로, 21명은 학생 18명·GM 3명·이동 3명으로 설정한다.

자동 검사와 개발 DB 관련 통합 테스트의 실제 결과는 해당 변경의 완료 기록을 기준으로 한다. 이전 버전의 테스트 수·Preview 성공을 새 GM 모드 결과로 재사용하지 않는다. [GM 운영 안내](gm-mode.md)의 구현·검증 기록을 확인한다. 실제 사람의 대화 효과, 실물 기기·현장 Wi-Fi, 21명 규모의 부하 검증은 각각 별도다.
